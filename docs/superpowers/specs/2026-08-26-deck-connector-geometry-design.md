# Deck Connector Geometry Design

**Date:** 26 August 2026
**Status:** Approved in chat; awaiting written-spec review
**Scope:** Module 1 deck correction and a reusable course-local deck generation pipeline

## Problem

The Module 1 deck was generated by `/tmp/build-m1-deck.mjs`. The generated HTML is committed, but the generator is not. Its generic `loop()` helper always starts an edge at the source rectangle's right midpoint and ends at the destination rectangle's left midpoint. That rule works across the top row but makes return edges travel through the lower and right-side nodes. The `hub()` helper similarly starts every edge at the center of the central rectangle, so lines can cross the central label before leaving the box.

The visible defects are not isolated drawing mistakes. They are geometry defects in reusable primitives. Static HTML patching would repair the current screenshots but reproduce the problem the next time the deck is generated.

## Goals

1. Correct every connector-bearing diagram in the 61-slide Module 1 deck.
2. Generate connectors from rectangle boundaries using explicit ports.
3. Prevent connectors from crossing nodes or their labels.
4. Validate arrow direction, endpoints, slide numbering, and generated-output freshness.
5. Make deck generation, validation, and visual review repeatable with repository commands.
6. Preserve the approved lesson titles, slide order, narration alignment, visual style, and learner-facing content.

## Non-goals

- Redesigning the CourseSmith whiteboard visual language.
- Changing the Module 1 curriculum or voiceover.
- Adding a browser automation dependency to the learner application.
- Modifying the installed CourseSmith plugin during this course-local repair. The geometry library will be suitable for a later upstream change after it proves stable here.

## Geometry model

Every connected box is a named node:

```js
{
  id: 'observe',
  x: 810,
  y: 145,
  width: 170,
  height: 70
}
```

The geometry library exposes boundary ports:

```text
top    = x + width / 2, y
right  = x + width,     y + height / 2
bottom = x + width / 2, y + height
left   = x,             y + height / 2
```

An edge names its semantic direction and route:

```js
{
  id: 'observe-to-verify',
  from: 'observe',
  fromPort: 'bottom',
  to: 'verify',
  toPort: 'right',
  route: 'clockwise-corner'
}
```

Generated node groups carry `data-node-id`. Generated paths carry `data-edge-id`, `data-from`, `data-to`, `data-from-port`, and `data-to-port`. These attributes do not change rendering; they make the geometry independently testable.

## Connector rules

### Pipeline

Horizontal pipelines connect `source.right` to `target.left`. The existing visual form remains unchanged, but generated metadata and endpoint validation are added.

### Clockwise loop

Loop nodes occupy a fixed ring. The route is explicit rather than inferred from one universal right-to-left formula:

```text
left-middle.right  -> upper-left.left
upper-left.right   -> upper-right.left
upper-right.right  -> right-middle.left
right-middle.bottom -> lower-right.right
lower-right.left   -> lower-left.right, when a lower-left node exists
lower-left.left    -> left-middle.bottom
lower-right.left   -> left-middle.bottom, for a five-node loop
```

Corner routes use cubic curves whose control points remain outside the source and target rectangles. The final tangent points toward the target port, so the arrowhead communicates the declared semantic direction.

This corrects loop slides 6, 7, 19, and 32.

### Hub

Hub connectors follow the ray between the central-node center and satellite-node center, but the visible line begins where that ray exits the central rectangle and ends where it enters the satellite rectangle. No connector begins at the central center or crosses its label.

This corrects hub slides 3, 10, 23, 27, 30, and 60.

### Other visuals

The validator audits every slide. `compare`, `cards`, `ladder`, `boundary`, and `icons` contain no semantic arrow edges. Their decorative lines are not assigned edge metadata. Every pipeline, loop, and hub connector is assigned metadata and validated.

## Collision validation

The generated deck fails validation when any of these conditions is true:

1. A connector endpoint is not on the declared source or target boundary port.
2. A connector ends without `marker-end`.
3. An edge's declared `from` or `to` node does not exist on the same slide.
4. A sampled line or cubic-curve point enters an unrelated node rectangle expanded by a six-pixel clearance.
5. A connector remains inside its source or target rectangle after the boundary endpoint tolerance.
6. The final path tangent points away from the target port.
7. Two slides use the same page number.
8. Page numbers are not exactly `M1.01` through `M1.61` in order.
9. The deck contains a different number of slides, titles, content slides, or dividers than the approved sequence.
10. Regenerating the deck produces output different from the committed HTML.

Labels live inside their node rectangles. Preventing paths from entering rectangles therefore prevents paths from crossing node labels. Slide titles, subtitles, footers, and page numbers remain outside the diagram view box and are covered by the existing deck-layout audit.

## Generation flow

`build-m1-deck.mjs` reads the checked-in Module 1 slide specification, renders through the shared primitives, combines it with a checked-in CourseSmith-compatible deck shell, validates the result, and writes the final HTML only after validation passes.

The temporary absolute paths are removed. Repository paths resolve from `import.meta.url`, so the command works from any current directory.

The slide specification contains exactly one entry for every numbered slide. Duplicate or missing slide numbers fail before HTML generation.

## Commands

The site `package.json` will expose:

```bash
npm run deck:m1
npm run deck:check
npm run deck:render:m1
```

- `deck:m1` regenerates Module 1 and validates it.
- `deck:check` runs geometry tests, validates the committed deck, and compares it with a fresh generated copy.
- `deck:render:m1` uses `CHROME_BIN` when set, otherwise detects common Chrome locations. It renders all 61 slides at 1280 by 720, advances each slide to its final fragment state, and writes an HTML contact sheet.

The rendering command is an authoring tool. It is not part of the Docusaurus runtime and is not required by learners.

## Error handling

- Missing deck shell, Chrome binary, slide specification, or output directory produces a named error with the required path or environment variable.
- Validation reports the slide number, edge ID, conflicting node ID, and first collision point.
- Generation writes to a temporary file first. The committed deck is replaced only after validation succeeds.
- A failed visual-render command leaves the validated HTML unchanged and reports which slide failed to capture.

## Test strategy

### Unit tests

- Every port returns the hand-calculated boundary coordinate.
- Straight and curved routes begin and end on the requested ports.
- A deliberately crossing connector fails with the conflicting node ID.
- A clean clockwise connector passes.
- A reversed final tangent fails direction validation.

### Deck contract tests

- Slides are numbered 1 through 61 exactly once.
- The deck contains 10 dividers and 51 content slides.
- Every semantic connector has metadata and an arrowhead.
- All connector paths pass collision and direction validation.
- The checked-in deck equals fresh generator output.
- The existing self-contained, size, subtitle, accessibility, and narration-marker audits remain green.

### Visual QA

- Render all 61 slides and review the contact sheet for overall consistency.
- Inspect all ten connector-bearing slides at full size and final fragment state.
- Confirm slides 6 and 7 use clean clockwise loops with no path crossing a box or label.
- Build Docusaurus, render the embedded deck, and verify the fullscreen public asset.

## Release sequence

1. Add failing geometry tests against the current connector behavior.
2. Check in the generator and slide specification without changing learner content.
3. Implement boundary ports and collision-safe routes.
4. Regenerate the deck.
5. Run unit, deck, CourseSmith, TypeScript, and Docusaurus build checks.
6. Render and inspect the 61-slide contact sheet and all connector slides.
7. Commit, push, deploy, and verify the public deck.

## Acceptance criteria

- No semantic connector intersects a node other than at its declared source and target boundary points.
- No connector crosses a node label.
- Every arrowhead points toward its declared target.
- Slides 6, 7, 19, and 32 read as clockwise loops without ambiguous return paths.
- Hub connectors begin and end at box boundaries on slides 3, 10, 23, 27, 30, and 60.
- `npm run deck:m1`, `npm run deck:check`, `npm run typecheck`, and `npm run build` exit zero.
- The complete deck renders successfully and remains aligned with the approved narration.
